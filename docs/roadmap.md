# 首版范围与实施计划

[返回文档导航](README.md) · [项目介绍](../README.md)

本文描述计划交付的能力、实施阶段及验收方向，不代表功能已经实现。组件职责以[架构设计](architecture.md)为准，协议细节后续单独设计。

## 1. 项目目标与首版范围

项目希望提供统一入口，让用户能够发现 Agent、了解能力、配置调用方式，并进行持续对话和任务执行。

首版需要打通：

**服务实例注册 → Manager 配置 Agent → Dispatch 同步路由 → 客户端指定 Agent → 服务执行 → 返回执行过程与结果。**

| 功能 | 首版方向 |
| --- | --- |
| 三个程序 | 同一 Go 仓库构建 Manager、Dispatch、Daemon 三个可执行程序 |
| 现成 Agent 封装 | Daemon 通过后端适配器接入 Codex、Claude 等 Agent，具体接入方式与顺序后续确定 |
| 标准服务接入 | Daemon 和第三方服务通过相同的接入机制注册、续约及报告就绪状态 |
| Agent 管理 | Manager 维护 Agent ID、服务绑定、能力描述、调用配置与启用状态 |
| 路由订阅 | Dispatch 同步完整调用所需的配置、实例及有效状态 |
| 对话与执行 | 客户端指定 Agent，创建会话、提交任务并获得执行结果 |
| 状态管理 | 区分平台会话、原生 Agent 会话、一次执行和工作区 |
| 记录与权限 | 保存必要的对话和执行记录，校验接入、调用与会话访问权限 |

首版暂不包含根据自然语言自动选择 Agent、多 Agent 协作、工作流编排、定时任务、知识库、计费、多租户、Manager 集群和跨实例自动迁移会话。

流式输出、进度、取消、用户确认和结果查询需要纳入后续协议设计；首版支持哪些操作及交互界面，在协议设计阶段确定。文件和图片等多模态输入另行规划。

## 2. 实施阶段与验收方向

### 阶段一：设计标准协议与适配边界

明确接入、订阅、会话和执行协议，确定首版必选能力、可选操作、认证方式及故障语义。分别确认 Codex、Claude 等后端的接入和状态管理方式。

### 阶段二：实现最小闭环

实现三个 Go 程序、必要持久化、至少一种现成 Agent 适配器，以及一个独立实现标准协议的演示服务，验证：

1. Daemon 注册自身并直接接受 Dispatch 调用，底层 Agent 能完成真实任务。
2. 演示服务无需部署 Daemon，也能注册并经 Dispatch 调用。
3. Manager 可配置 Agent ID、服务绑定和能力描述，配置可传播到 Dispatch。
4. 实例及后端状态、租约变化可影响新会话的实例选择。
5. 多轮交互保持实例及原生会话关联，不因 Dispatch 扩容而丢失绑定。
6. 原实例不可用时不自动迁移或重放，会话状态与工作区边界表达清楚。
7. 重连、配置传播、Manager 与 Dispatch 异常恢复符合后续协议约定。
8. 重复请求、超时、取消和用户确认按首版支持范围验证，不支持的操作有明确结果。
9. 未授权接入、调用、会话或工作区访问被拒绝，凭证不泄露。

### 阶段三：完善后端与使用体验

增加更多后端适配器、管理与聊天页面、接入 SDK、复杂调度和 Manager 高可用。会话迁移、执行环境恢复及跨实例故障接管在具备状态恢复条件后另行设计。

## 3. 待进一步讨论

- Codex、Claude 等后端的首版接入顺序和具体程序化接口。
- Daemon 的部署单元、执行资源隔离、并发限制与工作区分配。
- 标准协议的必选能力，以及流式事件、取消、结果查询和用户确认的首版范围。
- 原生会话及工作区的持久化、重启恢复和清理方式。
- 一个服务关联多个 Agent ID 时的执行配置和生效方式。
- 注册、心跳、路由传播、租约和最大陈旧时间等运行参数。
- 用户身份、会话可见范围、内容保留要求与 Web 页面交付范围。

后续协议和实现说明应沿用[架构设计](architecture.md)中的职责边界，并明确区分已确定的架构、待确认的设计与已实现的行为。
